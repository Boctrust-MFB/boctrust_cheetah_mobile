# User Notification Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the notification placeholder with the authenticated user's persistent inbox and wire up all seven documented `/api/v1/users/me/notifications` operations.

**Architecture:** Add a notification model and service over the existing authenticated User Service `ApiService`, then session-scoped Riverpod state for the active list, deleted list, and unread count. The Notifications screen owns list filters, pagination, and actions; the Home bell watches the unread count. Existing FCM delivery and `/auth/fcm-token` registration remain the push transport, while an incoming push triggers inbox and count refresh.

**Tech Stack:** Flutter, Dart, Riverpod, Dio, `flutter_test`.

**Spec:** [BocTrust User Service API, User Notifications](https://user-dev-api.centurysoftware.dev/api/v1/docs/#/User%20Notifications)

## Global Constraints

- Include only the seven authenticated `/api/v1/users/me/notifications` operations. Exclude every `/internal/...` operation, including those grouped under User Notifications.
- Use `apiServiceProvider`, whose base URL already includes `/api/v1`; endpoint constants must omit that prefix.
- Attach an `ApiCallLabel` to every service request, as required by `test/api_call_label_coverage_test.dart`.
- Keep private notification content in memory only and clear it on sign-out, session expiry, and account switch.
- Use server `notificationId` values for mutations. Do not use the integer ID generated by `NotificationPayload` for local OS notifications.
- Do not interpret arbitrary server `metadata`, `resourceType`, or `resourceId` as a route. Opening a row may show its message and mark it read; navigation needs an explicit, separately reviewed mapping.
- Do not change notification preferences, Firebase registration, or push-display copy as part of this inbox work.

## API Coverage

| Method | Path relative to User Service base | App behavior |
| --- | --- | --- |
| GET | `/users/me/notifications` | Active inbox, status/date filters, page/limit |
| GET | `/users/me/notifications/deleted` | Read-only deleted view, same filters and pagination |
| GET | `/users/me/notifications/unread-count` | Home bell badge and inbox count |
| POST | `/users/me/notifications/mark-all-read` | Mark all active notifications read |
| PATCH | `/users/me/notifications/{id}/read` | Mark one active notification read |
| PATCH | `/users/me/notifications/{id}/unread` | Mark one active notification unread |
| DELETE | `/users/me/notifications/{id}` | Soft-delete one active notification |

Swagger lists `status=unread|read`, `fromDate` and `toDate` as dates, `page` default 1, and `limit` default 20 for both lists. The list response has `data.items` and `data.pagination` (`page`, `limit`, `total`, `totalPages`). An item has `notificationId`, `type`, `title`, `message`, `status`, optional resource fields, `metadata`, `createdAt`, and optional `readAt`. Other responses have `data.unreadCount`, `data.updated`, a returned notification, or `data.deleted`, respectively. Mutations by ID document a 404 response.

## Review Focus

1. A previous user's pending response arrives after account switch: it must not populate the new user's inbox or count. Test in Task 3.
2. A mutation succeeds while a stale page load is pending: the old load must not restore the prior status or deleted row. Test in Task 3.
3. A failed refresh follows a successful load: keep the last good list visible with an error and Retry; never claim the inbox is empty. Test in Tasks 3 and 4.
4. The last row on a page is deleted: reconcile pagination from the server rather than leaving a blank page with more results elsewhere. Test in Task 3.
5. A push arrives while Home is visible: refresh the unread count once without showing sensitive server content in the local notification. Test in Task 5.

## Acceptance Criteria

- Every documented user notification endpoint is called by a reachable app flow and has a contract test.
- Home and Notifications show the server's unread count and records; errors remain distinguishable from an empty inbox.
- Read, unread, mark-all-read, and soft-delete actions reconcile list and count from server-confirmed results.
- Deleted notifications are viewable but cannot be restored by the app because no restore endpoint is documented.
- Logout, session expiry, account switch, and late responses cannot reveal a previous user's notifications.
- No mobile request targets a path beginning `/internal/`.
